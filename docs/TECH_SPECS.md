# Плагин in-employee-reports

## Общее описание функциональности плагина

Плагин `in-employee-reports` предназначен для заполнения и проверки отчетов сотрудников "Иван Никитин и партнеры" по выполненным задачам на отдельной странице в личном кабинете сайта.
### Страница отчетов

Представляет собой обычную страницу WordPress с размещенным шорткодом плагина.

На странице выводится:
- Строка управления со следующими компонентами:
	- Сотрудник
		- Выпадающий список со значениями "Все" и все пользователи WordPress с ролью `employee`
		- Значение по умолчанию: имя текущего авторизованного пользователя
	- Месяц
		- Выпадающий список
		- Перечисление месяцев: Январь - Декабрь
		- Значение по умолчанию: текущий месяц
	- Год
		- Поле ввода
		- Значение по умолчанию: текущий год
	- Кнопка Показать
		- Перезапрашивает и обновляет данные в таблице
	- Кнопка Экспорт
		- Выполняет загрузку данных в таблице с текущими фильтрами в файл в формате CSV
- Строка статистики
	- Число записей: текущее число записей в таблице
	- Часов: сумма по полю "Кол." (число часов) по данным таблицы
	- Сумма: сумма("Кол" * "Ставка") по данным таблицы
- Таблица
	- Редактируемая и автоматически сохраняемая таблица с данными отчета

#### Таблица отчета

Редактируемая таблица дает возможность заполнения и редактирования данных так, как это делается при использовании Google таблиц или Excel. 

Наполнение таблицы данными происходит при входе на страницу или при нажатии на кнопку "Показать".

Сохранение данных происходит при перемещении курсора или активной ячейки в любую другую строку, через 5 секунд после прекращения редактирования (по возможности) или при выходе со страницы.

Создание новой строки происходит заполнении пустой строки под данными либо по клику в меню по правой кнопке мышки в выпадающем меню "Добавить строку". Строка добавляется вниз.

Удаление любой строки происходит по клику правой кнопки мышки в выпадающем меню "Удалить строку".

Колонки таблицы:

- `Код` -- ID записи WordPress. Ячейка доступна только для чтения, редактирование невозможно. Для новой строки сначала создается запись в БД WordPress и заполняется ID созданной записи. 
-  `Сотрудник` -- Имя и фамилия сотрудника. для новой строки всегда заполняется по имени текущего авторизованного пользователя. Ячейка доступна только для чтения, редактирование невозможно.
- `Дата` -- Дата заполнения строки, для новой строки заполняется текущей датой, может редактироваться.
- `Проект` -- Тестовое поле проекта, заполняется текстом, по возможности сделать подсказку по ранее заполненным данным.
- `Кол.` -- Количество часов, потраченных на задачу. Числовое поле с дробными данными float. Разделитель дробной части определяется текущей локалью пользователя.
-  `Ставка` -- Ставка за выполнение задачи. Числовое поле с дробными данными float и указанием символа валюты Разделитель дробной части и денежная единица определяется текущей локалью пользователя.
- `Сумма` -- вычисляемое поле `Кол.` * `Ставка`,  редактирование невозможно.

### Хранение данных в БД WordPress

Данные сохраняются в виде записей в типом записей (Custom Post Type) `activity`:

- Пользователь сохраняется как  `author` (`$post->post_author->display_name`)
- Дата -- дата записи (`$post->post_date`) 
- Проект -- мета-поле записи `_activity_project`
- Кол. -- мета-поле записи `_activity_quo`
- Ставка -- мета-поле записи `_activity_rate`

## Права пользователей

Плагин предназначен только для использования сотрудниками компании. Доступ к данным в админке WordPress ограничен ТОЛЬКО пользователями входящими в заданные группы и администраторам. 

Плагин использует две роли  пользователей:

- Роль `employee` -- сотрудники. Плагин должен разрешать просмотр только СВОИХ, созданных этим пользователем записей. Выборка пользователей по этой роли -- это полный список сотрудников для фильтров, описанных выше. 
- Роль `head_of_department` -- руководители. Могут просматривать отчеты всех сотрудников.

Если ролей нет, их следует создать. Роль `employee` создается на базе роли `contributor`, роль `head_of_department` создается на базе роли `editor`.

В текущей реализации плагина более сложная схема ролей с тремя ролями (employee, head_of_department, head). Ее следует переработать и упростить до двух ролей по указанным выше правилам. Роль `head` должна быть удалена, а существующие пользователи с этой ролью автоматически мигрированы на роль `head_of_department`. 

## Страница настроек

В текущей реализации плагина страница настроек предназначена для генерации паролей приложений для доступа к REST API. Следует полностью отказаться от этой функции и использовать стандартные пароли приложений WordPress. 

Страницу настроек можно полностью убрать.

## Текущая реализация функций плагина

### 1. Главный файл плагина (`source/in-employee-reports.php`)

*   **Назначение:** Точка входа плагина. Определяет метаданные плагина, обеспечивает безопасность и инициализирует основные компоненты.
*   **Ключевые функции:**
    *   **Заголовок плагина:** Содержит стандартную информацию о плагине (название, описание, версия, автор, лицензия и т.д.).
    *   **Проверка безопасности:** Защищает файл от прямого доступа.
    *   **Встроенный автозагрузчик классов:** Использует `spl_autoload_register()` для автоматической загрузки классов плагина из папки `classes/`. Плагин самодостаточен и не требует установки зависимостей Composer для работы.
    *   **Глобальные константы:** Определяет константы `INER` (текстовый домен), `INER_FOLDER` (путь к папке плагина) и `INER_URL` (URL к папке плагина).
    *   **Хук активации (`iner_activation`):** Вызывается при активации плагина, инициализирует пользовательские роли и возможности через `RoleManager::initRoles()`.
    *   **Хук инициализации (`iner_init`):** Вызывается при загрузке плагинов, загружает текстовый домен для локализации и создает экземпляр основного класса `InEmployeeReports\\Plugin`.

### 2. Основной класс плагина (`source/classes/Plugin.php`)

*   **Назначение:** Центральный координатор плагина. Управляет жизненным циклом других ключевых компонентов и предоставляет механизм логирования.
*   **Ключевые свойства:**
    *   `path` (string): Абсолютный путь к папке плагина.
    *   `url` (string): URL к папке плагина.
    *   `report` (InEmployeeReports\\Report): Экземпляр класса для управления отчетами.
    *   `frontend` (InEmployeeReports\\Frontend): Экземпляр класса для фронтенд-логики.
    *   `settings` (InEmployeeReports\\Settings): Экземпляр класса для управления настройками.
*   **Ключевые методы:**
    *   **Конструктор (`__construct`):** Инициализирует пути и URL плагина. Регистрирует метод `init()` для выполнения после инициализации WordPress, если пользователь авторизован.
    *   **`init()`:** Создает экземпляры классов `Report`, `Frontend` и `Settings`, передавая им ссылку на себя (`$this`) для обеспечения взаимодействия.
    *   **`log($log, $message)` (private):** Вспомогательный метод для записи сообщений в указанные файлы логов (`activity.log`, `error.log`). Работает только в режиме отладки (`WP_DEBUG`).
    *   **`activityLog($message)`:** Записывает сообщения в лог активности.
    *   **`errorLog($message)`:** Записывает сообщения в лог ошибок.

### 3. Класс управления отчетами (`source/classes/Report.php`)

*   **Назначение:** Полностью управляет пользовательским типом записи "Активность" (Activity CPT) в WordPress, включая его регистрацию, отображение в админке, сохранение данных и интеграцию с REST API.
*   **Ключевые константы:**
    *   `CPT` (string): Идентификатор пользовательского типа записи (`activity`).
    *   `FIELD_*`: Константы для названий полей отчета (`id`, `employee`, `date`, `project`, `quo`, `rate`, `comment`).
    *   `META_*`: Константы для ключей мета-полей (`_activity_project`, `_activity_quo`, `_activity_rate`).
    *   `NONCE_METABOX`: Ключ nonce для безопасности метабокса.
*   **Ключевые методы:**
    *   **Конструктор (`__construct`):** Регистрирует CPT, хуки для загрузки стилей админки, метабоксов, колонок в таблице списка записей, фильтрации записей по пользователям и маршрутов REST API.
    *   **`registerCPT()` (private):** Регистрирует CPT `activity` с заданными метками, поддержкой полей (`title`, `author`) и пользовательскими возможностями (capabilities), определенными в `RoleManager`. Устанавливает `Activity_REST_Controller` как контроллер для REST API этого CPT.
    *   **`loadCSS($hook)`:** Регистрирует и подключает `admin.css` и `jquery-ui-datepicker` для админ-панели.
    *   **`addMetabox()`:** Регистрирует метабокс "Данные для отчета" на странице редактирования CPT `activity`.
    *   **`showMetabox($post, $box)`:** Отображает поля метабокса для ввода даты, проекта, объема и ставки. Использует `jquery-ui-datepicker` для поля даты.
    *   **`saveMetabox($postID, $post)`:** Обрабатывает сохранение данных из метабокса, включая проверку nonce, фильтрацию ввода и обновление `post_date` и пользовательских мета-полей.
    *   **`getAdminColumns($columns)`:** Изменяет стандартные колонки в таблице списка записей CPT `activity`, добавляя пользовательские поля и переименовывая некоторые стандартные.
    *   **`showAdminColumns($column, $postId)`:** Выводит содержимое для каждой колонки в таблице списка записей, включая расчет "Суммы".
    *   **`getSortableAdminColumns($sortableColumns)`:** Определяет, какие колонки в админке могут быть отсортированы.
    *   **`setUsersFilter($query)`:** Применяет фильтрацию к запросам CPT `activity` в админке, показывая пользователям только те отчеты, к которым у них есть доступ (через `RoleManager::getAllowedUsers()`). Администраторы видят все записи.
    *   **`registerRoutes()`:** Создает экземпляр `Activity_REST_Controller` и регистрирует его маршруты REST API.

### 4. Класс для фронтенда (`source/classes/Frontend.php`)

*   **Назначение:** Отвечает за отображение интерфейса отчетов на фронтенде сайта, включая подключение скриптов/стилей и обработку шорткодов.
*   **Ключевые константы:**
    *   `SHORTCODE` (string): Идентификатор шорткода (`in_employee_reports`).
*   **Ключевые методы:**
    *   **Конструктор (`__construct`):** Регистрирует хук `wp_enqueue_scripts` для загрузки фронтенд-активов и шорткод `in_employee_reports`.
    *   **`loadAssets()`:** Условно (только для авторизованных пользователей) регистрирует и подключает стили и скрипты `Handsontable` (в будушем AG Grid) и собственные скрипты плагина. Использует `wp_localize_script` для передачи JavaScript-переменных, таких как REST API URL, nonce, ID текущего пользователя, списки сотрудников и проектов.
    *   **`getHTML($atts, $content = '')`:** Callback-функция для шорткода.
        *   Выполняет перенаправление на страницу авторизации, если пользователь не залогинен.
        *   Обрабатывает атрибуты шорткода.
        *   **Непосредственно подключает стили и скрипты `handsontable` и плагина.** (Примечание: это дублирует логику `loadAssets` и может быть упрощено при рефакторинге).
        *   Генерирует HTML-разметку для интерфейса отчетов, включая элементы управления фильтрацией (выпадающие списки для сотрудников, месяца, года), кнопку "Показать", области для отображения итогов и контейнер для таблицы.

### 5. Класс REST контроллера (`source/classes/activity-rest-controller.php`)

*   **Назначение:** Предоставляет REST API для выполнения CRUD-операций (Создание, Чтение, Обновление, Удаление) над записями отчетов. Расширяет стандартный контроллер WordPress для постов.
*   **Наследование:** Расширяет `WP_REST_Posts_Controller`.
*   **Ключевые методы:**
    *   **Конструктор (`__construct`):** Устанавливает пространство имен `/reports/v2` и имя ресурса `activity` для REST API.
    *   **`register_routes()`:** Регистрирует маршруты для коллекции записей (`/activity`) и для отдельных записей (`/activity/(?P<id>[\d]+)`). Определяет методы (GET, POST, PUT, PATCH, DELETE) и соответствующие функции-колбэки, а также функции для проверки разрешений.
    *   **`get_item_schema()`:** Возвращает JSON-схему данных для записи отчета, описывая все поля (`id`, `employee`, `date`, `project`, `quo`, `rate`, `comment`), их типы и свойства (`readonly`).
    *   **`get_items_permissions_check($request)`:** Проверяет права на получение списка отчетов. Включает проверку авторизации пользователя (в том числе через пароли приложений с использованием `RoleManager`) и наличие общей возможности `READ_ACTIVITY`.
    *   **`get_items($request)`:** Получает список записей отчетов, используя параметры запроса для фильтрации по сотруднику, году и месяцу. Применяет фильтрацию на основе `RoleManager::getAllowedUsers()`.
    *   **`prepare_response_for_collection($response)`:** Вспомогательный метод для форматирования ответа коллекции.
    *   **`get_item_permissions_check($request)`:** Проверяет права на доступ к конкретной записи отчета, используя `RoleManager::canDo()` с учетом возможностей `READ_ACTIVITY` и `READ_OTHER_ACTIVITIES`.
    *   **`get_item($request)`:** Получает данные одной записи отчета по ID.
    *   **`prepare_item_for_response($post, $request)`:** Преобразует объект `WP_Post` в массив, соответствующий JSON-схеме, включая данные из мета-полей.
    *   **`create_item_permissions_check($request)`:** Проверяет права на создание новой записи отчета (`CREATE_ACTIVITY`).
    *   **`create_item($request)`:** Создает новую запись отчета, обрабатывает входные данные, сохраняет их как пост и мета-поля.
    *   **`update_item_permissions_check($request)`:** Проверяет права на обновление записи отчета (`EDIT_ACTIVITY`, `EDIT_OTHER_ACTIVITIES`).
    *   **`update_item($request)`:** Обновляет существующую запись отчета.
    *   **`delete_item_permissions_check($request)`:** Проверяет права на удаление записи отчета (`DELETE_ACTIVITY`, `DELETE_OTHER_ACTIVITIES`).
    *   **`delete_item($request)`:** Удаляет запись отчета.

### 6. Класс управления ролями и разрешениями (`source/classes/RoleManager.php`)

*   **Назначение:** Управляет пользовательскими ролями и возможностями (capabilities) плагина, а также реализует механизм аутентификации через пароли приложений.
*   **Ключевые свойства:**
    *   `$roles` (static array): Массив, определяющий пользовательские роли (`employee`, `head_of_department`, `head`) с их названиями, базовыми ролями WordPress и специфическими для плагина возможностями.
*   **Ключевые константы:**
    *   `READ_ACTIVITY`, `EDIT_ACTIVITY`, `DELETE_ACTIVITY`, `CREATE_ACTIVITY`: Возможности для работы со *своими* отчетами.
    *   `READ_OTHER_ACTIVITIES`, `EDIT_OTHER_ACTIVITIES`, `DELETE_OTHER_ACTIVITIES`: Возможности для работы с *чужими* отчетами.
    *   `APP_PASS_*`: Константы для работы с паролями приложений (ключи для мета-полей и кэша).
*   **Ключевые методы:**
    *   **`initRoles()` (static):** Вызывается при активации плагина. Регистрирует пользовательские роли и устанавливает для них соответствующие возможности. Также добавляет все возможности плагина администраторам.
    *   **`canDo($postId, $userId, $ownCap, $otherCap)` (static):** Основная функция для проверки прав доступа к объекту. Определяет, может ли `$userId` выполнить действие (`$ownCap` или `$otherCap`) над `$postId`. Учитывает роли пользователя и принадлежность записи (своя/чужая).
    *   **`user_can($userId, $capability)` (static):** Проверяет, обладает ли пользователь (`$userId`) указанной возможностью (`$capability`), учитывая все его роли.
    *   **`getAllowedUsers($userId)` (static):** Возвращает список ID пользователей, отчеты которых разрешено просматривать пользователю `$userId`. Использует фильтр `in-employee-department-users` для расширения.
    *   **`generateKey($param = '')` (static):** Генерирует уникальный ключ (используется для паролей приложений).
    *   **`getApplicationPasswords()` (static):** Получает все пароли приложений, хранящиеся у пользователей, которые имеют доступ к отчетам. Результат кэшируется в транзиентах.
    *   **`authentificateApplication($key, $secret)` (static):** Аутентифицирует пользователя по ключу и секрету приложения. В случае успеха авторизует пользователя в WordPress.

### 7. Класс настроек (`source/classes/Settings.php`)

*   **Назначение:** Управляет глобальными настройками плагина и предоставляет интерфейс в админ-панели для генерации и управления паролями приложений.
*   **Ключевые свойства:**
    *   `_name` (string): Имя опции в базе данных WordPress (совпадает с именем класса).
    *   `_params` (array): Массив для хранения общих настроек плагина.
    *   `appPasswords` (array): Массив для хранения паролей приложений текущего пользователя.
*   **Ключевые методы:**
    *   **Конструктор (`__construct`):** Загружает существующие настройки и пароли приложений. Регистрирует страницу настроек в админ-меню.
    *   **`load()`:** Загружает общие настройки плагина из опций WordPress и пароли приложений текущего пользователя из `user_meta`.
    *   **`save()`:** Сохраняет общие настройки плагина в опции WordPress и пароли приложений текущего пользователя в `user_meta`. Удаляет кэш паролей приложений.
    *   **`get($param, $default = false)`:** Получает значение параметра из настроек, возвращая значение по умолчанию, если параметр отсутствует или пуст.
    *   **`set($param, $value)`:** Устанавливает значение параметра в настройках.
    *   **`__get($param)` / `__set($param, $value)` (магические методы):** Позволяют обращаться к параметрам настроек как к свойствам объекта.
    *   **`addSettingsPage()`:** Добавляет пункт "Настройки" в меню "Отчеты" в админ-панели WordPress.
    *   **`showSettingsPage()`:** Отображает HTML-форму страницы настроек. Обрабатывает POST-запросы для создания и удаления паролей приложений, выполняет проверку nonce и сохраняет изменения.


## Архитектура и ключевые компоненты (после рефакторинга)

### Принципы рефакторинга (KISS)
Основная цель рефакторинга — максимальное упрощение кода и использование стандартных, надежных механизмов ядра WordPress.

1.  **Упрощение системы кастомных ролей:** Вместо трех ролей (employee, head_of_department, head) плагин будет создавать только **две кастомные роли**:
    *   `employee` (Сотрудник) — на базе роли `contributor`, с правами просмотра/редактирования/удаления/создания только СВОИХ отчетов
    *   `head_of_department` (Руководитель) — на базе роли `editor`, с правами просмотра/редактирования/удаления ВСЕХ отчетов
    *   Роль `head` удаляется, существующие пользователи автоматически мигрируются на `head_of_department`
2.  **Использование `map_meta_cap`:** Вся сложная логика проверки прав доступа будет делегирована ядру WordPress через хук `map_meta_cap`. Это позволит использовать стандартные функции типа `current_user_can('edit_post', $post_id)` во всем плагине.
3.  **Отказ от кастомных паролей приложений:** Самописная система аутентификации будет полностью удалена в пользу **встроенных паролей приложений WordPress**, которые доступны в профиле каждого пользователя.

**Схема ролей после рефакторинга:**

```
employee:
├─ Базовая роль: contributor
├─ Права: просмотр/редактирование/удаление/создание СВОИХ отчетов
└─ Capabilities: read_activity, edit_activity, delete_activity, create_activity

head_of_department:
├─ Базовая роль: editor
├─ Права: просмотр/редактирование/удаление ВСЕХ отчетов, создание своих
└─ Capabilities: все от employee + read_others_activities, edit_others_activities, delete_others_activities

administrator:
├─ Стандартная роль WordPress
└─ Получает все capabilities плагина автоматически
```

### 1. Главный файл плагина (`source/in-employee-reports.php`)
*   **Назначение:** Точка входа плагина.
*   **Логика:**
    *   При активации плагина (`register_activation_hook`) вызывает метод `Permissions_Manager::initRoles()` для создания кастомных ролей `employee` и `head_of_department` и метод `Permissions_Manager::migrate_old_roles()` для миграции пользователей со старой роли `head`.
    *   При инициализации (`init`) подключает хук `map_meta_cap` для управления правами доступа.
    *   При загрузке (`plugins_loaded`) инициализирует главный класс плагина `Plugin`.

### 2. Основной класс плагина (`source/classes/Plugin.php`)
*   **Назначение:** Центральный координатор плагина.
*   **Логика:** Остается практически неизменной. Инициализирует и хранит экземпляры классов `Report`, `Frontend`, `Settings`. Управление правами осуществляется через статические методы класса `Permissions_Manager`.

### 3. Класс управления разрешениями (`source/classes/Permissions_Manager.php`) - (Замена `RoleManager`)
*   **Назначение:** Управляет кастомными ролями `employee` и `head_of_department`, их разрешениями (capabilities) и привязкой к стандартным механизмам WordPress через `map_meta_cap`.
*   **Ключевые методы:**
    *   **`initRoles()` (static):** Вызывается при активации плагина. Создает две кастомные роли:
        *   `employee` — на базе `contributor` с правами `read_activity`, `edit_activity`, `delete_activity`, `create_activity`
        *   `head_of_department` — на базе `editor` с дополнительными правами `read_others_activities`, `edit_others_activities`, `delete_others_activities`
        *   Также добавляет все capabilities администраторам
    *   **`migrate_old_roles()` (static):** Находит всех пользователей с ролью `head`, меняет их роль на `head_of_department` и удаляет роль `head` из системы.
    *   **`map_meta_cap($caps, $cap, $user_id, $args)`:** Подключается к хуку `map_meta_cap`. Это **ключевой метод** для упрощения логики. Он "объясняет" WordPress, как обрабатывать стандартные запросы прав (`edit_post`, `read_post`, `delete_post`) для CPT `activity`. Например, если WordPress проверяет `current_user_can('edit_post', $post_id)`, этот метод:
        1.  Определяет, что `$post_id` — это запись типа `activity`.
        2.  Проверяет, является ли `$user_id` автором записи.
        3.  Вместо `edit_post` требует от пользователя наличие `edit_activity` (если он автор) или `edit_others_activities` (если не автор).
        Таким образом, вся сложная логика инкапсулируется здесь, а в остальном коде используются простые и стандартные проверки.

### 4. Класс управления отчетами (`source/classes/Report.php`)
*   **Назначение:** Управляет CPT "Активность".
*   **Изменения:**
    *   В методе `registerCPT()` будет упрощена секция `capabilities`. Вместо перечисления всех примитивных типов будет использоваться `'capability_type' => 'activity'`, а также `map_meta_cap => true`. Это стандартный способ сообщить WordPress, что для данного CPT нужно использовать `map_meta_cap` для определения прав.

### 5. Класс REST контроллера (`source/classes/activity-rest-controller.php`)
*   **Назначение:** Предоставляет REST API для CRUD-операций.
*   **Изменения:**
    *   **Упрощение проверки прав:** Все методы `..._permissions_check` будут значительно упрощены. Вместо вызова `RoleManager::canDo()` они будут использовать стандартные проверки WordPress:
        *   `get_items_permissions_check`: `current_user_can('edit_posts')` (или `read`).
        *   `get_item_permissions_check`: `current_user_can('read_post', $post_id)`.
        *   `update_item_permissions_check`: `current_user_can('edit_post', $post_id)`.
        *   И так далее для всех операций.
    *   **Удаление аутентификации:** Код, связанный с `RoleManager::authentificateApplication()`, будет полностью удален. Контроллер будет полагаться на стандартную аутентификацию WordPress (куки или встроенные пароли приложений).

### 6. Класс настроек (`source/classes/Settings.php`)
*   **Назначение:** Управляет настройками плагина.
*   **Изменения:**
    *   **Удаление управления паролями:** Вся логика, связанная со свойством `appPasswords` (загрузка, сохранение, генерация ключей), будет удалена.
    *   **Изменение интерфейса:** Страница настроек в админ-панели (`showSettingsPage`) больше не будет отображать таблицу с ключами. Вместо этого там будет размещен информационный текст, объясняющий администраторам, что для интеграции с внешними приложениями (например, Excel) необходимо использовать **встроенные пароли приложений**, которые каждый пользователь может сгенерировать в своем профиле (`Пользователи` -> `Профиль`). Это перекладывает ответственность за безопасность на ядро WordPress.

### 7. Класс для фронтенда (`source/classes/Frontend.php`)
*   **Назначение:** Отображение интерфейса на фронтенде.
*   **Изменения:** Архитектурных изменений, связанных с `RoleManager`, здесь нет. Основные изменения коснутся замены `Handsontable` на `AG Grid`, как описано в предыдущем разделе.

## Рефакторинг Frontend: Замена таблицы отчетов

### Проблема

Текущая реализация таблицы для ввода и редактирования отчетов использует библиотеку Handsontable. В ходе эксплуатации были выявлены следующие недостатки:
- **Низкая производительность:** Таблица начинает "тормозить" и медленно реагировать при увеличении количества данных.
- **Нестабильность:** Иногда возникают непредвиденные ошибки ("глюки") при взаимодействии с таблицей.
- **Пользовательский опыт:** Интерфейс не в полной мере соответствует ожиданиям пользователей, привыкших к плавности и функциональности Google Sheets или MS Excel.

### Задача

Произвести рефакторинг фронтенд-части, заменив компонент `Handsontable` на более производительное и функциональное решение, обеспечивающее максимально простой и интуитивно понятный интерфейс для редактирования данных, сравнимый с настольными табличными редакторами.

### Рекомендуемое решение: AG Grid

В качестве новой основы для таблицы предлагается использовать библиотеку **AG Grid (Community Version)**.

**Обоснование выбора:**

1.  **Высочайшая производительность:** AG Grid спроектирован для работы с большими объемами данных. Он использует технику **виртуализации DOM (Row and Column Virtualization)**, отрисовывая только видимые пользователю ячейки. Это позволяет ему без задержек обрабатывать десятки и сотни тысяч строк.
2.  **Богатая функциональность "из коробки":** Бесплатная версия предоставляет все необходимые функции для создания интерфейса в стиле Excel:
    *   Редактирование ячеек по клику или двойному клику.
    *   Продвинутая сортировка и фильтрация.
    *   Изменение ширины и перетаскивание колонок.
    *   Копирование/вставка данных (в том числе из Excel).
    *   Закрепление колонок.
3.  **Простота интеграции:** Библиотека легко устанавливается через `npm` и интегрируется в существующий процесс сборки. Базовая настройка для создания редактируемой таблицы проста и интуитивно понятна.
4.  **Качественная документация:** AG Grid обладает одной из лучших документаций на рынке, с интерактивными примерами для чистого JavaScript, что упрощает разработку.

### План миграции

Переход на AG Grid будет осуществляться по следующим шагам:

1.  **Установка зависимости:** Добавить `ag-grid-community` в `package.json` и установить через `npm`.
2.  **Обновление сборки:** Модифицировать `build`-скрипт в `package.json` для копирования необходимых CSS-тем и JS-файла AG Grid из `node_modules` в папку `source/assets/dist`.
3.  **Обновление PHP-кода:** В файле `source/classes/frontend.php` изменить вызовы `wp_register_style` и `wp_register_script`, чтобы они подключали ассеты AG Grid вместо Handsontable.
4.  **Рефакторинг JavaScript:** Полностью переписать логику инициализации таблицы в `source/assets/js/frontend.js`:
    *   Определить структуру колонок (`columnDefs`).
    *   Сконфигурировать опции таблицы (`gridOptions`), включая включение редактирования, сортировки и т.д.
    *   Инициализировать AG Grid на соответствующем `div`-элементе в HTML-разметке шорткода.
5.  **Интеграция с REST API:**
    *   Логика загрузки данных будет адаптирована для передачи массива записей в `gridOptions.api.setRowData()`.
    *   Сохранение изменений будет реализовано через обработчик событий AG Grid, например, `onCellValueChanged`. При изменении ячейки будет отправляться запрос на соответствующий REST-эндпоинт для обновления записи в базе данных.

## Функционал экспорта данных в CSV

### Описание

Необходимо добавить кнопку "Экспорт" в строке фильтров. При нажатии на эту кнопку все данные, которые в данный момент отображаются в таблице (с учетом примененных фильтров и сортировки), должны быть выгружены в формате CSV. Файл должен быть скачан на компьютер пользователя.

### Техническая реализация (Frontend)

1.  **Интерфейс:**
    *   В HTML-разметке, генерируемой шорткодом, будет добавлена кнопка `<button id="exportCsv">Экспорт в CSV</button>`.
    *   Кнопка должна располагаться логично, например, рядом с элементами управления фильтрацией таблицы.
2.  **JavaScript (frontend.js):**
    *   Будет добавлен обработчик события `click` для кнопки "Экспорт".
    *   При срабатывании события, будет вызван метод AG Grid API `exportDataAsCsv()`. Этот метод по умолчанию экспортирует только видимые строки с учетом фильтров и сортировки.
    *   Дополнительно можно будет настроить параметры экспорта, такие как разделитель, кодировка и имя файла.

### Техническая реализация (Backend - PHP)

*   Для данной функциональности **не требуется дополнительных изменений на стороне Backend (PHP)**, так как AG Grid осуществляет экспорт данных, которые уже загружены на клиенте и отображаются в таблице. Запросы к REST API для этой задачи не нужны.
